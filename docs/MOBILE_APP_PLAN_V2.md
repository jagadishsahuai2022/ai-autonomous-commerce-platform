## 1. Why I'm Revisiting v1

v1 assumed `apps/mobile/` inside the existing Turborepo. That is the *fastest* path for a 1–2 dev team that already lives in this monorepo. But you asked the right questions: **what are the risks, and would a separate repo be cleaner?** This document answers both honestly.

The short version: **the monorepo (v1) is operationally cheaper but couples release cadence and CI cost; the separate repo (this doc's recommendation) is operationally heavier upfront but pays back the moment you have (a) a mobile-only contributor, (b) a release that needs to ship without web/API touching it, or (c) any vendor / contractor working on mobile only.**

## 3. Repository Topology Options

Three serious options. I'll evaluate each on the same axes.

### Option A — **Monorepo** (v1's path)
Everything stays in `delegatecart/`; mobile is `apps/mobile/`.

```
delegatecart/                       (single repo)
├── apps/
│   ├── web/      api/      ai-service/  …
│   └── mobile/   ← NEW
└── packages/
    ├── types/    ui/       design-system/  ← NEW
```

**When this wins:** solo dev or 2-person team that always context-switches across the stack; need to share types/3D/design-system frictionlessly; willing to invest in Metro+pnpm+Turbo glue once.

**When it loses:** see §2.

### Option B — **Two-repo (Recommended)**
`delegatecart/` stays as-is (web + API + Python services). New repo `delegatecart-mobile/` holds the React Native app. Both grouped under a GitHub Organization (e.g. `delegatecart-org`). Shared TypeScript types published from `delegatecart` to GitHub Packages (npm) and consumed by mobile.

```
GitHub Organization: delegatecart
├── delegatecart/                 (existing — web, API, ai-service, infra, docs)
│   └── publishes:
│       └── @delegatecart/types  →  GitHub Packages npm registry
│       └── @delegatecart/sdk    →  generated from OpenAPI (auto-publish on release)
│
├── delegatecart-mobile/          ← NEW (RN + Expo, iOS + Android together)
│   ├── consumes @delegatecart/types
│   ├── consumes @delegatecart/sdk
│   └── ships to App Store + Play Store
│
└── delegatecart-design/          ← OPTIONAL (design tokens + Figma exports)
    └── publishes @delegatecart/design-tokens  (consumed by web AND mobile)
```

**Wins:**
- Mobile CI is fast & cheap (only mobile changes trigger it).
- App Store rejection / hotfix doesn't entangle web/API.
- Mobile-only contractor gets `delegatecart-mobile` repo only — backend stays private.
- VS Code workspace for mobile devs is light & RN-tuned (different ESLint, TS, Metro).
- Existing repo stops growing → web typecheck timeout problem you fought last week doesn't get worse.
- Independent versioning: `delegatecart-mobile` uses semver `1.x.y` for store submissions; `delegatecart` continues its release cadence.
- Can later extract `ai-service` or `infra` into their own repos under the same org without disrupting either.

**Losses:**
- Type sharing requires a publishing pipeline (~1 day to set up, runs forever).
- A breaking API change is now a *coordinated release* across two repos (mitigated by SDK versioning + deprecation windows).
- Bigger upfront setup (≈ 2 days work to wire publish + consume).
- Two issue trackers (or one Project board spanning both — see §4).

### Option C — **Three-repo (only if/when you split iOS & Android)**
`delegatecart/` + `delegatecart-mobile-ios/` (Swift/SwiftUI native) + `delegatecart-mobile-android/` (Kotlin/Compose native).

```
GitHub Organization: delegatecart
├── delegatecart/                 (web, API, services)
├── delegatecart-mobile-ios/      (Swift, SwiftUI, Xcode)
└── delegatecart-mobile-android/  (Kotlin, Compose, Gradle)
```

**When this wins:** you have separate iOS and Android teams with deep platform expertise; you need *bleeding-edge* native features that React Native can't expose without custom modules; you have the budget to maintain ~2× the surface area indefinitely.

**When it loses:** today. Per §2 in v1, native split = 3× engineering cost for a v1 product still finding its mobile fit. Code reuse drops from ~95% to 0%.

**My counsel:** **plan for it as a *future* migration**, not a starting point. The migration path from Option B → Option C is non-trivial but well-trodden (Airbnb famously did the reverse: native → RN); document it now, decide later.

### Side-by-side comparison

| Axis | A — Monorepo | **B — 2 repos (recommended)** | C — 3 repos (native split) |
|---|---|---|---|
| Setup cost | Lowest (~½ day) | Medium (~2 days) | Highest (~1 week per platform) |
| Steady-state DX | Degrades over time | Stable & isolated | Excellent per platform |
| Code reuse iOS↔Android | 95%+ (single RN codebase) | 95%+ (single RN codebase) | ~0% (two native codebases) |
| Code/type reuse with web | 100% (in-tree imports) | ~80% (via published packages) | ~0% (no shared lang) |
| CI cost & speed | Couples to monorepo | Independent, fast | Independent per platform |
| Release independence | Poor | Excellent | Excellent |
| Onboarding mobile-only contributor | Poor (gets full access) | Excellent | Excellent |
| App Store rejection blast radius | High | Low | Lowest |
| Open-source flexibility | Low | High | Highest |
| Platform-specific UX ceiling | Good | Good (RN limits) | Best (native) |
| Talent pool | TS / React devs | TS / React devs | Swift + Kotlin specialists |
| Maintenance cost (3-yr horizon) | Med-rising | Med-stable | High-stable |
| Migration to other option | A→B easy; A→C hard | B→C is a rewrite | C→B is a rewrite |
| **Recommended for DelegateCart today?** | If 1 dev | **YES** | Not yet |

## 4. GitHub Organization Strategy (so split repos still feel like one product)

This is the lever that makes Option B feel as cohesive as a monorepo.

### 4.1 Organization layout
```
github.com/delegatecart                  (org)
├── delegatecart                          (web + API + services + infra + docs)
├── delegatecart-mobile                   (RN app — iOS + Android)
├── delegatecart-design        (optional) (tokens + Figma exports + brand assets)
├── delegatecart-sdk-ts        (optional) (auto-generated from OpenAPI)
└── .github                               (org-level templates, CODEOWNERS, security policy)
```

### 4.2 Cross-repo cohesion mechanisms

| Mechanism | Purpose |
|---|---|
| **GitHub Projects (v2) — cross-repo board** | Single Kanban: columns = `Backlog / Ready / In progress / In review / Done`. Tasks come from any repo. Same sprint planning everywhere. |
| **Org-level CODEOWNERS** + per-repo CODEOWNERS | Auto-assign reviewers across boundaries. |
| **Org-level secrets** (Dependabot, Sentry token, npm publish PAT) | Single place to rotate. |
| **GitHub Packages npm registry** | Hosts `@delegatecart/types`, `@delegatecart/sdk`, `@delegatecart/design-tokens`. Free for private packages within org limits. |
| **GitHub Container Registry** | Already used for backend; mobile EAS Build uses cloud, not GHCR. |
| **Reusable workflows** (`.github/workflows/*.yml` in `.github` repo) | DRY shared CI — typecheck, lint, security-scan workflows used by all repos via `uses: delegatecart/.github/workflows/typecheck.yml@main`. |
| **Org-wide labels & milestones** | `mobile-v1.0`, `api-v2.5` labels visible across repos. |
| **Single Linear / Jira workspace** (optional external PM tool) | Cross-repo issue linking. |
| **Single Slack channel + GitHub app** | All PRs, deploys, alerts in one place. |
| **Cross-repo ADRs (Architecture Decision Records)** in `delegatecart/docs/adr/` | One source of truth for architectural decisions affecting either side. |

### 4.3 Branching & release model (recommended)

| Repo | Branches | Release tag | Cadence |
|---|---|---|---|
| `delegatecart` | `main` (prod), `release` (staging integration), `develop` (default) | `web-vX.Y.Z`, `api-vX.Y.Z` | Continuous (web) / sprintly (API) |
| `delegatecart-mobile` | `main` (prod-released), `develop`, `feat/*` | `vX.Y.Z` (semver = store version) + build numbers per submit | App-store cycle (1–2 wk) |
| `@delegatecart/types` package | Versioned independently; published from `delegatecart`'s CI on merge to `develop` (prerelease) and `main` (stable) | npm semver | Per change |

### 4.4 Type & SDK sharing pipeline

```
[delegatecart repo]                              [delegatecart-mobile repo]
                                                  
packages/types/  ──┐                              package.json:
                   │                                 "@delegatecart/types": "^1.4.0"
   On merge:       │
   1. version bump │                              CI step:
   2. build .d.ts  │   GitHub Packages              pnpm install
   3. publish ─────┴─►  npm registry  ───────────►  uses latest matching version
                        @delegatecart/*
                                                  
apps/api/                                         metro resolver picks it up
   exports OpenAPI spec (build step)              like any other npm dep
   ↓                                              
sdk-generator job (GH Actions)
   openapi-typescript --input swagger.json
   commits to delegatecart-sdk-ts repo
   publishes @delegatecart/sdk
```

Bootstrap cost: 1–2 days. Steady-state cost: zero (fully automated).

### 4.5 Authentication for mobile devs against private packages
GitHub Personal Access Token (classic) with `read:packages` → set in mobile dev's `.npmrc`:
```
@delegatecart:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```
EAS Build is told the token via `eas.json` env. Same on local dev machines.

## 9. Backend Changes Required (unchanged from v1, restated)

These are *additive* and don't break web. ~9 small endpoints, ~1 PR each.

1. `POST /auth/refresh` — confirm exists & rotates refresh token.
